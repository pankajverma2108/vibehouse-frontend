# Payment Logging Enrichment — End-to-End Verification

**Date:** 2026-05-21  
**Backend:** `https://api.thedailysocial.co.in` (prod, revision 29, post commit [`e4c80fe`](https://github.com/Emagicor/deta/commit/e4c80fe) for payment enrichment + commit [`f83f03d`](https://github.com/Emagicor/deta/commit/f83f03d) for brand isolation)  
**Property tested:** Buteak (`55402`)  
**Test dates:** Dec 20–22 2026 (different from earlier tests to avoid collision)  
**Companion docs:**
- [`docs/plans/payment_logging_enrichment.md`](../plans/payment_logging_enrichment.md) — the plan
- [`docs/api_testing/buteak_booking_flow_e2e_2026-05-20.md`](buteak_booking_flow_e2e_2026-05-20.md) — first multi-property booking E2E

**Goal:** Prove the payment-logging enrichment works end-to-end on prod:
1. Razorpay order's `notes` field carries `property_id`, `property_name`, `purpose`, `purpose_label`, `guest_email`
2. `payments.property_id` is denormalized at order creation time (no join needed for ops queries)
3. After capture (simulated), the SQS → eZee chain enriches `Booking_Payment_Mode` + per-room `SpecialRequest` on the eZee booking
4. No regression on existing flows

✓ `property_id` is set at create-order time, not at capture. This means an ops query like:
```sql
SELECT count(*) FROM payments
WHERE property_id = '55402' AND status IN ('CREATED','CAPTURED','FAILED')
  AND created_at > now() - interval '7 days';
```
correctly accounts for all Buteak payments, including abandoned ones. The new `idx_payments_property_status_created` index supports this query without a sequential scan.

### Step 6: Simulate Razorpay capture

Switching from `/payment/dev/simulate-capture` requires `NODE_ENV=development` (enforced in `payment.service.ts:352`). Same trick as the previous E2E:

```bash

# 2. Force ECS redeploy (~3 min)
# 3. Hit simulate-capture
```

Dev-window: ~6 minutes total (flip + rollout + hit + flip + rollout). During the window `EmailService` skips real SES sends. Confirmed no organic guest signups landed during the test window (would have shown up in `guests.created_at` timestamps).

## Findings / follow-ups

1. **`purpose_label` cosmetic** — `"Booking — Apartment 1 x1 × 1, 2 nights"` has a doubled count. `ezee_booking_cache.room_type_name` is stored with the eZee "x1" suffix; we then append `"× ${no_of_guests}"`. Either strip the suffix or use a cleaner field. Minor — 30 min fix.
2. **Razorpay webhook E2E (real payment + signature verification)** — still paused; resume per the steps in `docs/plans/payment_logging_enrichment.md`. The dev-simulate path covers all of our new enrichments, but doesn't validate Razorpay's actual webhook delivery or our signature-verification code path.
3. **Visual verification in eZee for SpecialRequest / Booking_Payment_Mode** — operator confirms whether the fields actually surface in eZee's UI. If not, follow-up to switch to AddExtraCharge for itemized notes.
4. **Addon + colive flows** — code path is identical (same enrichment, same eZee insert worker), but no E2E run yet.
